# 架构与数据流

## 1. 总体架构

从代码层面看，项目的核心执行链路是：

```text
data_loader
  -> compression.registry / compression.spectral
  -> FactorizedTemporalStore
  -> QueryEngine
  -> QueryIndexManager + index/*
  -> evaluation/*
  -> scripts/*
```

更具体地说：

1. `data_loader` 负责产生时序图快照序列。
2. `compression` 将快照压缩为 `FactorizedTemporalStore`。
3. `query_engine` 在 store 上实现 Q1-Q5。
4. `index` 为 Q2/Q3/Q4 提供加速结构。
5. `evaluation` 负责实验配置、指标计算与结果落盘。
6. `scripts` 作为顶层入口，把这些能力组织成可复现实验流程。

## 2. 核心对象关系

### 2.1 `FactorizedTemporalStore`

这是整个系统的中心数据模型，负责承载压缩结果和残差信息。

它包含：

- `left`: 源节点因子矩阵
- `right`: 目标节点因子矩阵
- `temporal`: 时间因子矩阵
- `lambdas`: 分量权重
- `residuals`: 稀疏残差
- `threshold_diagnostics`: 阈值与门控诊断信息
- 误差界相关元数据，如 `bound_sigma_max`、`bound_mu`

它既是压缩器的输出，也是 `QueryEngine` 的唯一必需输入。

### 2.2 `QueryEngine`

这是查询执行层的主入口，负责：

- 提供 Q1-Q5 API
- 封装误差界返回结构
- 管理 Q2 多路径执行
- 通过 `QueryIndexManager` 构建/挂载/持久化索引
- 在 Q3/Q4 路径上利用缓存和索引

### 2.3 `QueryIndexManager`

该类是 `QueryEngine` 与 `index/` 子包之间的桥接层。

它的职责包括：

- 构建 exact/ANN/PQ/IVFPQ/external/materialized 等 Q2 索引
- 构建 Q3 的 `CommunityInvertedIndex`
- 构建 Q4 的 `TemporalTrendIndex`
- 保存和加载索引产物
- 统一维护 manifest

### 2.4 `Q2PathPlanner`

这是 Q2 的语义路由器，不是单纯的“算法选择器”。

它根据查询语义做路径决策：

- `background` / `normal` / `factor_only`
  - 优先 materialized factor-only 路径
- `observed` / `event` / `observed_event`
  - 优先 exact index + residual rerank 路径

这体现了项目的 query-semantics-aware 设计。

## 3. 数据流详解

### 3.1 压缩主链路

```text
原始快照 snapshots
  -> create_compressor(name, config)
  -> compressor.fit_transform(snapshots)
  -> FactorizedTemporalStore
```

压缩器由 `compression/registry.py` 中的注册表统一调度。实验脚本一般不会直接实例化某个压缩器，而是通过字符串名字和配置生成。

### 3.2 查询主链路

```text
FactorizedTemporalStore
  -> QueryEngine(store, ...)
  -> Q1/Q2/Q3/Q4/Q5
  -> 标量结果 / 批量结果 / 带误差界结果
```

其中：

- Q1 直接调用 `store.link_score()`
- Q2 可走扫描、exact、ANN、PQ、IVFPQ、materialized、external ANN、residual rerank 等多路径
- Q3 默认用 KMeans 生成社区标签，也可走倒排索引
- Q4 可直接逐时刻扫描，也可利用时间趋势索引
- Q5 基于残差矩阵阈值检测异常

### 3.3 实验主链路

实验脚本一般遵循以下步骤：

```text
解析参数
  -> load_experiment_config()
  -> 加载或生成数据集
  -> 创建压缩器并压缩
  -> 构建 QueryEngine
  -> 运行 workload
  -> 统计指标
  -> 写出 csv/json/md/yaml 结果
```

`scripts/exp3/run_query_benchmark.py` 是最典型的代表，它几乎把整个系统链路串了一遍。

## 4. 模块依赖关系

### 4.1 内部依赖图

```text
data_loader  ------> scripts
compression ------> query_engine ------> scripts
index -----------> query_engine ------> scripts
evaluation ------> scripts
compression ------> evaluation (通过 store 做指标计算)
query_engine -----> evaluation (部分指标依赖 engine)
```

### 4.2 实际依赖特点

- `query_engine` 依赖 `compression`，因为它要读取 `FactorizedTemporalStore`。
- `query_engine` 依赖 `index`，因为索引是查询加速路径的一部分。
- `evaluation` 依赖 `compression` 和 `query_engine`，因为评估要读 store、也要跑查询。
- `scripts` 是最上层协调者，几乎依赖所有核心模块。

## 5. Q1-Q5 与底层实现映射

| 查询 | 默认实现思路 | 可选加速/优化 |
| --- | --- | --- |
| Q1 | 直接读取因子层或因子+残差层分数 | 误差界与残差启用策略 |
| Q2 | 扫描行分数 | exact / materialized / ANN / PQ / IVFPQ / external ANN / residual rerank / semantic planning |
| Q3 | KMeans 社区划分 | `CommunityInvertedIndex` |
| Q4 | 逐时刻调用 `link_score()` | `TemporalTrendIndex` + 缓存 |
| Q5 | 扫描残差矩阵 | batch 接口 |

## 6. 存储设计要点

### 6.1 因子化打分公式

`FactorizedTemporalStore` 中边 `(u, v)` 在时刻 `t` 的基础得分为：

```text
sum_j lambdas[j] * left[u, j] * right[v, j] * temporal[t, j]
```

若启用了残差，则最终得分会再加上 `residual_value(t, u, v)`。

### 6.2 残差存储格式

系统支持两种残差物理格式：

- `tuple[sparse.csr_matrix, ...]`
- `TemporalCOOResidualStore`

后者将所有时间片的残差统一编码为 `(t, row, col, value)` 的时序 COO 表，更适合统一访问与持久化。

### 6.3 存储门控

压缩模块中实现了 storage gate，用于避免残差层把压缩收益吞掉。相关配置包括：

- `max_sparse_ratio`
- `storage_gate_action`
- `residual_storage_format`
- `factor_storage_dtype_bytes`

这说明该项目不仅关心算法可行性，还明确把“压缩后真实占用多少字节”纳入系统设计。

## 7. 为什么该架构适合研究工程

这套架构的优点是：

- 能把方法实现、查询执行、索引结构、实验脚本分层。
- 能让单个组件独立复用和测试。
- 能支撑“同一套 store 上比较多种查询路径和索引路径”的实验需求。
- 能把方法贡献与系统贡献拆开表达，便于论文写作和证据管理。
