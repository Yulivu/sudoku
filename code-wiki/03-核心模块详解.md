# 核心模块详解

## 1. `compression/`

### 1.1 模块职责

`compression/` 负责把时序图快照压缩为统一的低秩存储表示，并可选生成稀疏残差、误差界元数据和存储诊断信息。

主要文件：

- `factorized_store.py`
- `spectral.py`
- `registry.py`

### 1.2 核心内容

#### `factorized_store.py`

定义整个系统最核心的数据结构：

- `TemporalCOOResidualStore`
- `FactorizedTemporalStore`

主要能力：

- 统一访问 link score、残差值、残差行、残差快照
- 计算压缩体积、元数据体积、相对稀疏图体积比
- 预计算与返回 entrywise error bound
- 用 NPZ 持久化压缩结果

#### `spectral.py`

定义压缩器配置与具体压缩器实现。

当前暴露或保留的主要压缩器包括：

- `UnifiedThinkingSpectralCompressor`
- `SymmetricSVDCompressor`
- `DirectSVDCompressor`
- `TensorUnfoldingSVDCompressor`
- `RPCASVDCompressor`
- `CPALSCompressor`
- `TuckerHOSVDCompressor`
- `NMFCompressor`

其中，当前项目主方法是：

- `spectralstore_thinking` -> `UnifiedThinkingSpectralCompressor`

该实现把以下机制放入统一流程：

- mode-3 / unfolding 思路
- ARD 秩选择
- robust residual thresholding
- 理论或经验误差界元数据写回 store

#### `registry.py`

这是压缩器注册中心，用字符串方法名映射到具体实现类。

典型调用方式：

```python
config = spectral_config_from_mapping(config_dict)
compressor = create_compressor("spectralstore_thinking", config)
store = compressor.fit_transform(snapshots)
```

这让实验脚本无需直接依赖具体类名。

## 2. `query_engine/`

### 2.1 模块职责

`query_engine/` 是系统的查询执行核心，负责把 `FactorizedTemporalStore` 暴露为可直接调用的 Q1-Q5 API。

主要文件：

- `engine.py`
- `planner.py`
- `index_manager.py`

### 2.2 `engine.py`

定义：

- `BoundedQueryResult`
- `QueryEngine`

`QueryEngine` 的职责可以分成五组：

1. Q1/Q4 的标量、批量和带误差界结果。
2. Q2 的多路径执行与残差 rerank。
3. Q3 的社区计算与社区索引接入。
4. Q4 的时间趋势查询、缓存与时间索引接入。
5. Q5 的残差异常检测。

Q2 是最复杂的一块，支持如下路径：

- 原始扫描
- factor-only 扫描
- factor + residual 扫描
- exact index
- materialized top-L index
- ANN prototype
- PQ prototype
- IVF-PQ prototype
- external ANN adapter
- 各类 candidate generation + residual rerank

### 2.3 `planner.py`

定义：

- `TopNeighborQueryPlan`
- `Q2PathPlanner`

它为 Q2 增加“语义规划”这一层：

- 背景/常规查询优先走 factor-only 或 materialized path
- 事件/观测查询优先走 exact index + residual rerank

这不是单纯性能优化，而是把查询语义显式编码进执行路径选择。

### 2.4 `index_manager.py`

`QueryIndexManager` 负责管理索引生命周期：

- build
- attach
- resolve
- save
- load

它统一屏蔽了不同索引的构建和持久化差异，使 `QueryEngine` 不需要直接处理每种索引的细节。

## 3. `index/`

### 3.1 模块职责

`index/` 提供压缩域查询所需的加速结构，尤其是 Q2/Q3/Q4。

主要文件与作用：

- `exact_mips.py`: 精确 MIPS 索引
- `ann_mips.py`: 随机投影 ANN 原型
- `pq_mips.py`: PQ-MIPS 原型
- `ivfpq_mips.py`: IVF-PQ 原型
- `external_ann_mips.py`: FAISS/HNSWLIB/NumPy 外部后端适配器
- `materialized_topk.py`: 预物化 top-L 候选
- `community.py`: 社区倒排索引
- `temporal.py`: 时间趋势索引与 B+ tree 风格结构

### 3.2 Q2 索引家族

Q2 的核心是做 target embedding 的 MIPS 检索。

不同索引的定位如下：

- `ExactMIPSIndex`
  - 最简单、最稳定的精确因子空间检索
- `RandomProjectionANNMIPSIndex`
  - 用随机投影做粗筛，再精排
- `ProductQuantizedMIPSIndex`
  - PQ 原型实现
- `IVFProductQuantizedMIPSIndex`
  - 带倒排桶的 IVF-PQ 原型
- `ExternalANNMIPSIndex`
  - 用外部库补充真实 ANN 后端
- `MaterializedTopKIndex`
  - 为每个 `(t, u)` 预计算 factor-only top-L

### 3.3 Q3 索引

`CommunityInvertedIndex` 将 `(time, community)` 映射到 member nodes，采用类似 CSR posting list 的方式组织数据，适合：

- 查询某个社区有哪些节点
- 查询某节点在某时刻属于哪个社区

### 3.4 Q4 索引

`TemporalTrendIndex` 把 factor temporal weights 组织到 `TemporalBPlusTree` 中，用于时间范围扫描。

特点：

- 不保存完整稠密快照
- 只保存时间权重与树结构
- 范围查询时通过叶节点扫描回收区间数据

## 4. `data_loader/`

### 4.1 模块职责

负责加载真实数据集和生成可控的合成数据。

主要文件：

- `bitcoin.py`
- `synthetic.py`
- `ogb.py`

### 4.2 `bitcoin.py`

定义了：

- `TemporalGraphDataset`
- `load_bitcoin_otc()`
- `load_bitcoin_alpha()`

数据处理逻辑：

- 读取 SNAP 数据行
- 按节点出现频率选前 `max_nodes`
- 按月聚合为时序快照
- 生成 `scipy.sparse.csr_matrix` 序列

### 4.3 `synthetic.py`

提供多种研究用生成器，例如：

- `make_low_rank_temporal_graph()`
- `make_temporal_sbm()`
- `make_theory_regime_sbm()`
- `make_temporal_correlated_sbm()`
- `make_synthetic_spiked()`
- `make_synthetic_attack()`
- `inject_sparse_corruption()`

这些生成器是 Exp1~Exp5 的重要数据来源。

## 5. `evaluation/`

### 5.1 模块职责

`evaluation/` 不是单纯的“打分函数集合”，它承担了实验工程契约的核心职责。

主要文件：

- `experiment.py`
- `metrics.py`
- `report.py`

### 5.2 `experiment.py`

负责：

- 加载 YAML 配置
- 校验 dotlist override 键是否合法
- 设置随机种子
- 检查 dense stack 的内存预算
- 写出统一实验产物
- 收集运行元数据、包版本、git 信息

### 5.3 `metrics.py`

负责：

- 重构误差类指标
- entrywise error / bound coverage 指标
- 社区聚类质量指标
- 异常检测精度召回指标

它既会直接消费 `FactorizedTemporalStore`，也会调用 `QueryEngine` 的查询能力做一些更偏系统侧的评估。

### 5.4 `report.py`

负责把底层数据整理成更适合实验汇报的结构，如：

- `storage_report()`
- `reconstruction_report()`
- `observed_edge_report()`
- `ranking_report()`

## 6. `scripts/`

### 6.1 模块职责

`scripts/` 是实际运行入口，而不是核心业务逻辑所在地。

分类如下：

- `scripts/data/`: 数据下载
- `scripts/exp1/`: 理论验证与边界实验
- `scripts/exp2/`: 压缩比与 residual gate 实验
- `scripts/exp3/`: 查询与索引实验
- `scripts/exp4/`: 历史攻击实验
- `scripts/exp4_v2/`: residual-query semantics / robustness 实验
- `scripts/exp5/`: ARD 诊断与选秩实验
- `scripts/hpc/`: HPC/AutoDL 批跑脚本

### 6.2 脚本设计约定

项目中明确强调：

- 脚本应尽量薄
- 核心逻辑应放在 `src/spectralstore/`
- 运行应通过显式 `--config` 提高可复现性

## 7. `experiments/configs/`

这是实验配置层，不是代码模块，但对理解系统非常重要。

特点：

- 采用 YAML + OmegaConf
- 按 `exp1` 到 `exp5` 分组
- 可通过 `--set key=value` 做覆盖
- 输出目录与参数组合高度依赖配置

它与 `scripts/` 配合构成项目的实验 DSL。
